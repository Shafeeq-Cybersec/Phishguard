Model Details

How PhishGuard detects phishing, explained simply.

Algorithm

  • Uses a Random Forest: 150 decision trees that each vote "phishing" or "safe".
  • The final answer is the majority vote across all trees.
  • Trees are constrained (max depth 20, min 20 samples per leaf) to avoid memorizing training data.

Dataset

  • Trained on Mitake/PhishingURLsANDBenignURLs from HuggingFace (~120K URLs).
  • Both phishing and safe URLs are full links with paths, so the model learns real patterns not just URL format.
  • Split 80% training, 20% testing. Classes are balanced 50/50.

Lesson learned: Our first dataset had safe URLs as bare domains (google.com) and phishing as deep links. The model got 99.4% accuracy by learning URL format, not phishing signals. We switched datasets to fix this.

Performance

86.5%test accuracy
0.94ROC-AUC
  • Accuracy means 86.5 out of 100 URLs are classified correctly on unseen data.
  • ROC-AUC of 0.94 means the model reliably ranks phishing URLs higher than safe ones. 1.0 is perfect, 0.5 is random guessing.
  • 86.5% on a clean dataset is more trustworthy than a "99%" result, which usually signals a data problem.

Feature Engineering

  • The model never visits the URL. It only reads the URL as text and extracts 22 structural signals.
  • These signals are called lexical features: things you can measure from the characters and words in the URL.
FeatureWhat it checksWhy it matters
url_lengthHow long is the URL?Phishing URLs are often very long to hide the real domain.
num_dotsHow many dots?More dots = more subdomains (e.g. paypal.com.evil.ru).
num_hyphensHow many hyphens?Attackers use hyphens to fake brand names: paypal-secure.com.
num_subdomainsHow deep is the subdomain?Deep nesting hides the real registered domain from users.
has_ipIs the host an IP address?Legitimate websites use domain names, not raw IPs like 192.168.0.1.
has_httpsDoes it use https?HTTPS alone does not mean safe. Phishing sites use it too.
has_at_symbolDoes it have an @ symbol?Browsers redirect to the part after @, so http://safe.com@evil.com goes to evil.com.
is_shortenedIs it a URL shortener?Shorteners (bit.ly, tinyurl) hide the real destination.
suspicious_word_countWords like login, verify, secure?Phishing pages copy login flows and use these words in the URL path.
suspicious_tldUnusual TLD like .zip or .review?These cheap TLDs are heavily used for phishing.
num_digitsHow many digits?Randomly generated phishing URLs tend to have many digits.
digit_ratioDigits as a fraction of URL length?Normalizes the digit count so short and long URLs are compared fairly.
longest_tokenLongest path segment?Long random tokens like /a3f9b2c1d8 are common in phishing links.
num_question_marksHas a query string?Complex query strings can hide obfuscated payloads.
num_ampersandsHow many parameters (&)?Many parameters often appear in phishing redirect chains.
num_equalsHow many = signs?Too many key=value pairs can signal excessive parameter abuse.
num_underscoresHow many underscores?Underscores in domain names are rare in legitimate websites.
num_percentHow many % characters?Percent-encoding (%20, %3D) can be used to obfuscate URLs.
num_slashesHow many slashes?Very deep paths with many slashes are common in phishing redirect chains.
path_lengthHow long is the path?Long paths often contain random junk to confuse scanners.
hostname_lengthHow long is the hostname?Long hostnames usually mean deep subdomain nesting or fake brand names.
num_at_symbolCount of @ in the URL?Multiple @ symbols are used in advanced redirect tricks.

URL Normalization

  • Before extracting features, https:// and leading www. are stripped from every URL.
  • This keeps the format consistent between training data and live user input.
User pastes https://www.google.com/search?q=flask
Normalized to google.com/search?q=flask model input
Without this fix, https://www.google.com had extra dots, slashes, and characters compared to how Google looked in training data. The model was flagging the real Google as phishing because of that mismatch.

Trusted Domain Allowlist

  • The model reads characters, not intent. Words like login and signin push the score higher even on real sites like paypal.com/signin.
  • A curated list of ~30 trusted brands overrides the model score when the registered domain is known safe.
  • Matching checks the actual registered domain, so paypal.com.evil.ru is NOT matched as PayPal. The real domain is evil.ru.

Limitations

  • Lexical only. The model never visits the URL. A clean-looking phishing link like x.co/abc may score low risk even if it leads to a malicious page.
  • False positives on auth words. Real sites with login or signin in the path can score higher. The allowlist covers known brands but not every legitimate site.
  • Static allowlist. The trusted domain list is manually maintained (~30 brands) and does not auto-update.
  • No threat intelligence. A brand-new phishing domain with a short, clean URL can evade detection until it shows structural red flags.
